# dsh-team — 本地团队插件（中文）

一个 `team` 工具管全队：派成员、随时换模型/思考强度、空闲成员自动领任务、免费模型台账自维护。
上下文只交一份工具 schema 的税（≈400 token），不建队、不设队长层、成员就是普通子代理会话。

## 装好就能用的 5 分钟剧本

在任意会话里直接说人话，模型会调 `team(action: …)`；下面是动作序列示例：

```
1  team(models)                      → 看现在哪些免费模型真能用（可派/沉底/白名单未开）
2  team(spawn, name:"w1", provider:"cline", model:"reflection/beam-free", effort:"max",
       task:"你是w1，先待命")           → 用指定模型+档位建一个成员
3  team(task, action2:"create", title:"抓竞品定价页", brief_path:"<你的写根>\\任务书.md", prio:5)
                                     → 往任务面板发一条任务（正文放文件，板上只放指针）
4  （w1 一空闲就自动领走 t1 开工，回"领到t1"；干完自己调 finish 结案）
5  team(status)                      → 每员一行：忙/闲 | want 路由 | actual 实际路由 | 当前任务 | 最近报错
6  team(retool, to:"w1", provider:"our-free-model", model:"kilo-auto/free", effort:"high")
                                     → 中途换模型+思考强度，成员的下一步就换新路由
7  team(msg, to:"w1", text:"…")      → 给成员追加指令（运行中的下一步边界送达）
8  team(kill, to:"w1")               → 打断当前一轮（不清收件箱）
```

## 右侧栏 Team 面板（零上下文）

按 `Ctrl+Alt+B` 展开右栏 → Team tab（与文件树/预览/终端并排）。三屏内容每 2.5 秒自动刷新：

- **成员**：灯（绿=running / 灰=cold·idle）+ 当前路由 + 心跳事件 + 流状态；出错行红字显最近报错。
- **任务板**：tid/状态/owner/标题实时列。
- **台账**：可派/失效/白名单未开/退避中计数 + top10 可派模型（带真派 ok 戳）。

数据走插件本地 API `/api/dsh-team/snapshot`，**不写会话日志、不进模型上下文**；面板是浏览器组件，token 成本恒为 0。

## status 行怎么读（含心跳）

`team(status)` 每员一行：`name|busy|evt|want|actual|task|error`

- `evt` = 成员最后一条已提交会话事件 + 距今秒数，例 `tool/call@ctx_execute@9s` = 9 秒前在执行 ctx_execute。**这是真进度心跳**——卡住的流照样显示 running，但 evt 会停着不走。
- 等模型输出且 5 秒无流帧时追加 `(流停Ns)`；跑工具期不显示（无流属正常）。
- `actual` = 成员 durable request header，只有真发过一次请求才会变，是换模生效的硬证据。

## action 一览

| action | 必填参数 | 干什么 |
|---|---|---|
| `spawn` | name, provider?, model?, effort?, demand?, **kind?, size?**, workdir?, teamName? | 建成员。**`provider`/`model` 可省**：省了插件按 `kind`+`size` 自己选路由，返回里带 `routeSetBy:"插件选型"` 和 `pickedBecause`（写明是"按标称筛的/真派过/无数据只能试"）。`effort` 可省：缺省按 `demand` 换算（缺省 d2 常规），且**永远不会超过该路由的实测封顶**。台账已标 `invalid`、正在退避的一律拒，并在错误里给出 3 条可派候选。**每个成员一个写根**：`workdir` 传绝对路径或 `"team"`（缺省 `<队目录>\<成员名>`），成员被钉 `workspace-write`，只能写这个目录（读全盘不受限）；`teamName` 缺省取任务简介 slug |
| `status` | scope?（mine/all） | 名册 + 板上 open 数 + 台账摘要（单次 <400 token）；`(卡住 Ns)`=工具调用超 120s 未回、`(loop×N)`=同错连续 ≥3 次，这两种才该 kill；`scope:"all"` 额外列别队成员 + 每队汇总 |
| `task` | action2 = create/list/finish/fail/**set/reopen/remove/accept/reject** | 任务面板：create 要 title，可带 body（**只写本片边界**：产出路径/验收命令，别抄 goal——派单消息会自动带上队伍总目标）/brief_path（任务书路径）/prio/**demand（推理强度 1\|2\|3\|max，缺省 2）**/**kind（grunt\|code\|design\|probe，选型偏好）**/**size（s\|m\|l\|xl = **输入**需要多大 ctx：128K/256K/1M/2M，缺省 m；超池子上限直接拒）**/caps/blocked_by/**owner（预指派，别的成员抢不走）**/**no_artifact（这单确实没有文件产物：true = `finish` 不再警告「产物无法核对」，见下）**；**产出大不用拆任务**，派单消息会按该路由的 out 标称值自动要求分批写文件；finish/fail 要 tid；**finish 之后是 `delivered` 不是 `done`（验收门，见下）**；**谁干这单谁结——只有 claimed 单的持有者能 finish/fail，队长对没人认领的单结单必须 `force:true`（板上会记「队长强制结单」）**；**accept/reject 只有队长能做**（accept: delivered→done 并解锁下游；reject: 打回 open，`force:true` 判 failed）；**set 原地改已有任务**（title/body/brief_path/artifacts/no_artifact/prio/caps/demand/kind/size/owner/blocked_by，`owner`/`blocked_by` 仅 open 可改，`demand` 会对正在跑该任务的成员立刻重算档位，`owner:"-"` 解除预指派）；**空 set 会被拒（以前会静默把它标成 reopened）**；**reopen 是真动作：failed/delivered/done → open 重干**（tid 不变、依赖不断；claimed 要先 fail，已是 open 的不用 reopen）；**前置 `failed` 视为依赖已结算**，不会永久锁死下游；成员异常结束时任务自动退回 open 并写明原因。**批量**：create 用 `tasks`（每项 title/body/…，顶层字段当共用默认，`{i}`=序号、`{prev}`=上一张 tid）一次建多张（先整体校验再建，不会留半批）；`remove`/`set` 用 `tids`（`"t3,t5,t7"` / 区间 `"t3-t7"` / 结尾那批 `">=t5"`，也能传数组）→ 编号批量删 / 同参数批量改；批量 set 某张改不了进 `skipped` 不连累别的，批量 remove 有一张被 claimed 且没给 `force:true` → 整批不动并点名 |
| `claim` | tid（+`to`?） | 手动认领一条 open 任务（自动领单之外的通道）；认领时按任务 demand 重算档位。**只认两种认领人**（2026-10-31 隔壁 8eaff90a 实测后补）：① 队员自己领（**不能写 `to`**，写了就是替别人抢单，直接拒）；② 队长自己干这单（不写 `to`，或写本队短号，`owner` 记成短号，这样它能直接 `finish` 不用 `force`）。名字既不是本队成员、也不是本队队长短号 → **直接拒**，并把本队可选成员名回给对方——原来这里照收不存在的名字（`to:"claimer-示例"`），把幽灵写进 `owner`，单从此挂在没人认的名下（自动派单不会给它、`holderOf` 找不到持有者），回执却写着 `claimed by claimer-示例`，看起来像成功 |
| `msg` | to, text | 给成员发消息/唤醒冷成员 |
| `retool` | to, provider, model, effort | 随时换模型和思考强度，下一步生效 |
| `kill` | to（+`remove`?） | 打断成员当前轮。`remove:true` = 同时**从名册移除腾名额**（它手上的任务仍留在板上）；不写则只叫停、成员留着可 `msg` 唤醒 |
| `history` | to（成员名）, filter?（子串） | 走 **DSH 自家 `sessionQuery`** 读该成员最近 8 条文本事件（消息/工具调用/结束原因）——成员到底说了什么、干到哪，唯一读回通道；只读，不改 |
| `models` | filter?（可选） | 台账紧凑摘要（计数 + top8 推荐 + **能力阶梯**，永不回全表）。**头部固定声明：ctx/out/eff 都是 catalog 标称值，不是实测；写「无数据」= 插件不知道，不能当无限**。行尾 `封顶:档` = 实测可用上限，`[占用:队/成员]` = 别的队正在用。能力阶梯给的是「ctx 标称 ≥1M/512K/256K/128K 各几条 + 无数据几条」和「单次输出最大多少 / ≥131K / ≥33K 各几条」——拆任务时照这张表定 `size` |
| `scan` | reset?（`"efforts"`） | 手动触发一次模型清单同步（内核 llm `listProviders`+`listModels` → OFM catalog → 探活 → OFM 实测账），补台账里没有的模型；`reset:"efforts"` 则清空实测封顶与档位拒绝记录。**不再调 python 扫描器**（2026-10-29 退役） |
| `save` | name2?（队名） | 把本队成员配置+任务板完成度镜像到 `<队伍目录>\<队名>.json`（队伍目录默认 `<.dsh 根>\team`，可在配置里改 `teamDir`）；注册后每 10s 随心跳自动刷新 |
| `teams` | — | 列 Teamstate 全部队伍：`队名|本队/🔒锁定/可认领|成员数|任务完成度|存于时间` |
| `adopt` | name2, force? | 复刻一支**原 Lead 会话已不存在**的队：任务板全量恢复、成员按档案路由重新 spawn（上下文不继承）；本会话已有板需 `force:true` |

## 成员权限：子代理只能干活，不能改队长的板

2026-10-31 隔壁 b080dbbf 的测试靶上出过最重的一次事故：自动成员 `auto2` **自己跑了全套队长动作**——`create t5/t6`、`claim(owner=manual)`、`set`、`save team-ac73137f.json`、`adopt`、`disband`。结果队长会话 `session-b080dbbf` 的板被当场换血：原 `t1|done,t2|done,t3|claimed` 全没了，只剩一张它自己建单重编号后的残单；`disband` 连队长板都拆得掉。

**根因不是成员"坏"**，是插件从来不问"调用方是不是队员"：`resolveLead()` 沿 `parentSession` 往上爬，队员调 `team` 拿到的正是队长板，而每个 `case` 只按 action 分派。还有两道隐藏的缝：

1. 老代码里判断"是不是成员"写成 `members.has(String(caller))` —— `members` 是按**子会话 UUID** 索引的，`String(agent)` 恒等于 `"[object Object]"`，**永远查不到** → 成员一律被当成队长，能 `force` 结单、能 `accept` 给自己盖章。
2. 成员被回收/移出名册之后，会话还活着；那时 `members.get(它)` 是 `undefined`，老代码又把它当队长放行——"残影成员还能 `disband` 队长板"就是这么来的。

**现在的规矩**：

- **成员动作白名单**：`task`(仅 list/finish/fail)、`claim`、`msg`(只能报本队队长)、`tell`、`files`、`history`、`status`。其余（`create/set/remove/accept/reject/save/adopt/disband/spawn/retool/kill/announce/scan/rule/goal/peers/teams`）一律拒，并在错误里点明"这是队长的活 + 用 `tell` 报给队长"。
- **判"是不是队员"用三重判据**：在册成员 / **已退役成员**（`retiredMembers` 表，回收·移除·收队·换血四处都登记）/ **父会话带板的子代理**（连档案里都没有的野生子会话也挡）。后两条专治"残影成员"。
- **成员的对外通道留了两条**：`msg(to:"<队长短号>")` 走邮局 + 唤醒队长；`tell(to:"<队长短号>")` 同理（同时修掉了原来的死路——`tell` 拿 `resolveLead` 出来的"我"去比收信人，成员报队长会被判成"to 是自己"）。
- **弱模型把交单写成 `action:"finish"`**（隔壁实录状态位出现 `unknown action finish`）现在会按 `task` + `action2` 同义转发；**不带 tid 就照旧报错**，不猜。

## 队伍归属与跨会话复刻

- 队伍默认**活在本对话框内**：成员和任务板都挂在当前会话（Lead）名下，别的会话互不干涉。
- `team(save)` 后队伍状态持续镜像到 `Teamstate\` 文件；**只要原 Lead 会话还存在（哪怕冷启动后没在用），别的会话 adopt 会被拒**——防"人没干活队被抢"。删掉那个对话，文件才变"可认领"。
- 新会话 `team(teams)` → 见"可认领" → `team(adopt, name2:"队名")`：任务板连完成度/回报摘要/产物指针原样复活，成员按各自路由重建待命（旧上下文不继承，产物文件才是记忆）。
- **队长在用保护**：Lead 当前实际在跑的模型（读 durable request header），成员 spawn/retool 选它会被直接拒绝，台账面板同步标"队长在用"；Lead 换模后自动释放。
- **面板按会话隔离**：右侧 Team 标签页带自己的会话 id 请求 `/api/dsh-team/snapshot?lead=<sessionId>`，只显示本队成员/任务/目标；别的队只给一行计数摘要（成员数、待/进行/完成），不出任务标题。开队（本队成员从 0 变成 >0）时自动把标签页弹出来，不会替换维护方正在看的标签页。
- **失败原文归档**：所有真派失败连同 `route@effort` 原文写进 `.state/errors.json`（最近 60 条），归因规则（含新增的「档位不支持」）就是照它补的；**同一份记录还按天追加到 `.state/errors/YYYY-MM-DD.jsonl`**（累计目录，不滚动、重启不丢，自动选路线后（D2）就靠它当证据基线）。`kind` 取值：`run-fail` / `model-fault` / `stall`。

## 跨会话来信：写到 `to` 就一定送到并叫醒

两个顶层对话框之间走插件自己的邮局（内核 `sendMessage` 只允许直接父子）：

| 通道 | 怎么发 | 什么时候会**主动叫醒**对方 |
|---|---|---|
| `tell` | `team(action:"tell", to:"<短号>", text:"…")` | **默认叫醒**：收信人由 `to` 字段决定，写了 `to` 就算指名（2026-10-31 修）。只有显式 `wake:false` 才纯投递 |
| `announce` | `team(action:"announce", text:"…")` | **默认叫醒**所有空闲的顶层会话（公告=需要你注意的事）；正在跑的不打断、排队进它下一步；`wake:false` 才纯投递 |

- **⚠ 2026-10-31 修的真事故（维护方报的）**：原来 `tell` 把收信人写在一等公民字段 `to` 里，代码却去**正文**里找 `@` 才决定叫不叫醒。c197654c 13:40:43 交了一份 1350 字的 TEAM 缺陷报告给 `to:"b87c7940"`，正文里一个 `@` 都没有 → 插件返回 `woke:false`，收信人从头到尾没被叫醒，是维护方在对话框里问「消息不是给你的？」才看见。**根因有两条，两条都堵了**：
  - ① **判据错位**：把「指名」当成正文内容去解析。现在 `addressed` 由 `to` 字段直接置真，正文里的 `@` 只作为额外确认，不再是否叫醒的前提。
  - ② **正文被硬截断**：投递时 `slice(0, 800)`，1350 字的报告尾巴（第 3~6 条建议）永远进不了信箱，而唯一的 `@` 正好落在第 943 字符之后——即使判据没错也永远命不中。现在整封留档（≤8K 全存，超长按首尾各 4K 折叠并**明写折叠标记**），超过 8K 的原文另落 `.state/mail-full/mail-*.txt`，交付时把路径写给收信人。
- **唤醒消息带整封全文**（2026-10-31 维护方定，原话「直接全文送达吧，我是发现了，不直接发你丫的根本懒得看」「消息不是插话送达？」）：唤醒走 `sessionController.prompt` 的 **steer**（插话进对方**当前回合**，它下一步就能看到），只有对方已空闲（内核报 `session/steer-unavailable`）才退回 followup 起一个新回合。文案给四件事——谁发的、多少字、**整封正文**——没有"去信箱取"这一步。超过 16000 字的信才折叠（前 12000 字 + 折叠标记 + 全文落 `.state/mail-full/`）。
- **`@` 只认「点名叫醒」这一种形态**（不再把正文里任何 `@` 当点名）：`@<收信人短号>`、`@<完整 session id>`、信头第一行的 `@你`。正文里的 `@别的会话`、`ops@example.com` 这类一律不认。老规矩「没点名只进信箱、不打断」照旧适用。
- **为什么最初不默认唤醒**（2026-10-30）：原来每递一条就 `sessionController.prompt` 把对方叫起来，等于拿维护方当信使——两个长跑会话会互相打断。现在的折中是：**`to` 明确写了就是"我要跟这个人说话"，该叫；正文没有 `@` 不代表没指名**。要避免打断就用 `wake:false`。
- **来信分两种标记**：明确点名的打 `❗@你 · 📨 来自 xxx`，其余 `📨 来自 xxx`；但**两种都整封交付**，不再因为是"普通来信"就砍内容。
- **箱子上限**：每个会话信箱 20 条、投递流水（面板「跨会话消息」）也是 20 条，超出的直接丢弃——**不保留历史、不显示累计**（原来留 100 条并显示「累计 N 条」，长跑会话会把 `leads-mail-log.json` 撑到无限大，维护方 10-30 明令去掉）。**面板摘要 300 字且带「共 N 字，全文见收件人信箱」标记**（2026-10-31 修：原来面板也按 800 字硬切且看不出被截）。
- 公告限频仍是**全体** 5 分钟最多一条（不是一人一条），一次最多叫醒 8 个空闲会话；成员（子会话）一律不广播。
- `team(peers)` 同时给出「其他会话」清单（含刚开、一句没说的空白会话），要拿新对话框当测试靶就从那里面挑短号。
- **⚠ 空白会话不会被唤醒**（2026-10-30 维护方抓到的真事故）：`blank:true` = 维护方开过那个对话、一句没说、还没落盘，侧栏里根本看不见它。`sessionController.prompt` 往里灌一句话，它就从"不存在"变成"有一条消息的会话"，标题生成器按内容起名——**等于插件替维护方造了一个新对话**（那次侧栏凭空冒出个叫「取信邮件」的窗口）。所以 `tell` 唤醒前先判 `blank`，是空白就只入信箱、绝不 prompt；等它自己发第一句、或维护方在 GUI 里用过一次，才允许叫醒。实现方的边界由此明确：**能开对话，但不许替维护方开**。
- **正文写多长不是插件管的事**（维护方 2026-10-31 定）：全文照送、**不设字数上限**、超限也不拦（只有 16000 字才为内核安全折叠）。插件只管**哪些字送进去**，管不了**该不该说**。要短是发信人的纪律，不是投递的机制——把上限做进投递，只会变成"截断了一份本来该说全的答复"。
- **该怎么写**（维护方 2026-10-31 定，硬规矩）：**在保证能说清楚问题的前提下尽可能简短；回答问题中的操作细节，没问就不发。** 落到操作上是三件事：① 结论先行——修没修好、对方要不要动手、要不要等回话；② 对方没问的**操作细节**（怎么修的、改了哪些文件、跑了什么验证、断言多少条）留在自己这边，不进正文；③ 对方问"修好没"就只回"修好了"，**不主动把修法附上**。这条写进了工具描述、`text` 参数说明和 `peers` 的 `how` 三处（同一句话出现三次，因为弱模型经常只看其中一处）。

## 验收门：finish 之后是 `delivered`，队长 accept 才 `done`

**为什么要有**（2026-10-31，采纳隔壁 c197654c 13:49:55 的建议，实现由实现方定）：插件只能验**"文件在不在"**（存在性 + mtime），验不了**"内容真不真"**。隔壁实测 t1/t8/t10 三次空心交付（json 全空字段）全部通过了 artifacts 检查并自动解锁下游，每次都造成连锁返工。

**状态机**：

```
open → claimed → (成员 finish) → delivered → (队长 accept) → done → 解锁下游
                      ↓                              ↑
                   (队长 reject) ──────────────→ open（下游继续挡着）
                                       或 force:true → failed
```

| 动作 | 谁能做 | 效果 |
|---|---|---|
| `finish` | **只有该单的持有者** | → **delivered**（待验收），**下游不解锁**；推「待验收」notice 给队长 |
| `accept` | **只有队长** | delivered → **done**，顺手 `sweepIdle` 解锁下游，返回值列出 `已解锁下游` |
| `reject` | **只有队长** | delivered → **open**（原成员可再抢），`force:true` 则判 failed；下游继续挡着 |
| `fail` | **只有该单的持有者** | → failed（依赖按已结算处理，不留死锁） |

### 状态流水（`trail`）：谁在什么时候把它改成什么，为什么（2026-10-31 定）

原来板上只有**一个当前状态**。after 验收门之后状态变多了（`open/claimed/delivered/done/failed`），
"t2 初始化显示 claimed，后来变 delivered"这种事就只能靠猜 —— 谁改的、什么时候、为什么，全都没有
（隔壁 8eaff90a 全量实测的问题 2）。

现在每张单都带 `trail`，**每一跳都留痕**：

```
{ at, from, to, by, why }   // by = 成员名 / 队长短号+（队长） / plugin；why 一句话说原因，截 120 字
```

- **先记后写**：`noteStatus()` 读的是赋值前的 `from`，所以调用约定是「先 `noteStatus` 再赋值」。
- **每一处状态赋值都记**：建单、自动派单、档位不够放回、ctx 不够放回、派单失败放回、重装孤儿退回、
  成员 finish/fail、队长 accept、reject 打回、reopen、成员被 remove 退回、异常结束退回、产物没落盘退回、
  自动结单、短回执退回、没回话退回。漏一处就等于那条路径还是黑箱。
- **不刷屏**：同一跳 3 秒内重复（自动派单和收尾两条路径撞车）合并成一条，只刷新时间。
- **不膨胀**：每单最多 20 跳，满了丢最旧的。
- **看得见**：`task(action2:"list")` 每行尾给最近一跳（`|轨迹 claimed→delivered@auto2 30s前（finish 交付，等队长验收）`）；
  `status` 里给完整流水（最近 6 跳，够还原"被退回几次、谁退回的"）；面板快照也带 `trail`（最近 8 跳）。


- **下游解锁判据统一收进 `taskSettled()`**：三处旧写法（补员判据、成员领单判据、spawn 前置判据）全部改成调它。**漏一处等于没做**，所以不许各处各写一套。
- `cfg.acceptGate: false` 可关掉（回到老行为 finish 即 done），给不想验收的队留后门；关掉时 `delivered` 也算已结，避免整板死锁。
- **成员不能验收自己的交付**——`accept/reject` 只认非成员的调用方。
- **产物声明：能补、也能正式承认"没有"**（2026-10-31 隔壁 8eaff90a 实测的问题 4）。`probe/code` 类不写 `artifacts` 时，建单和 `finish` 都会警告"产物无法核对"——警告本身没错，但没有**"本单确实没有文件产物"**的正式说法，于是每次交付都要被警告一遍，读起来像出错。现在两种收尾：
  - `task(action2:"set", tid:"tN", artifacts:"路径")` —— 补上要落盘的文件，之后 `finish` 按"存在 + mtime 晚于领单"硬核对（缺了就拒收）。
  - `no_artifact:true` —— 建单时带（`create` 参数）或 `set` 时写都行。板上记为 `noArtifact`，`finish` **不再推警告**，只在 `lastReport` 留一行 `[无文件产物，建单时已声明 no_artifact]`，回执写 `本单建单时已声明 no_artifact:true，不核产物`。**不写这个字段的照旧警告**——防线没被拆掉，只是给了"确实没有产物"一个正规出口。
- **结单必须是"干这活的人"发起**（2026-10-31 隔壁 b080dbbf 实测后补的硬闸）：原来队长对一张 `open` 且**根本没人认领**的单直接 `finish`，插件照样返回 `delivered`——没有成员干过活、没有产物、没有任何人声称完成，板上却写着"已交付待验收"。现在只有 `claimed` 且 `owner`/`currentTask` 都是调用方自己的单才能结；队长要越过人去结，必须 `force:true`，板上留 `forcedByLeadAt` + 「队长强制结单」的 `lastReport`，事后翻板子分得清是谁结的。
- 实测（2026-10-31 15:2x）：建 t1→t2 串行链，t1 `finish` 后状态 `delivered` 而 t2 **仍是 `open ←t1`（没有解锁）**；`accept(t1)` 返回 `{t1:"done（已验收）", 已解锁下游:["t2"]}`，随后 t2 立刻被空闲成员抢走。闭环成立。

### OFM 版本那一行：它自己升级，不走 npm（2026-10-31 修）

面板顶上那行 OFM 版本提示以前会报「⚠ OFM 声明 2.7.2 / 实装 2.7.3：装或卸任何插件都会退回 2.7.2」。
**那是误报**，而且它给的动作是错的。两条事实（维护方 2026-10-31 亲口定的）：

1. **OFM 由插件自己在线更新**：走仓库 `main` 的 `feed/manifest.json`，逐文件下载 + SHA256 校验，
   **不走 npm**。证据：`~/.dsh/our-free-model/upgrade-state.json` 记着
   `{"from":"2.7.2","to":"2.7.3","phase":"complete","activated":true}`。
2. **npm 上那个同名包不是同一个东西**：

   | | 官方（装在你机器上的） | npm registry |
   |---|---|---|
   | latest | **2.7.3** | **2.1.0** |
   | `private` | `true`（作者没打算发布） | 无此字段 |
   | repository | `Ebony-Vinyl/dsh-our-free-model` | **空** |
   | maintainer | — | `fish-under-sea` |

   所以真照旧提示去 npm 拉，装回来的是**别人的 2.1.0**。

现在这行只说两件**真事**：

| 状态 | 面板显示 |
|---|---|
| 官方有比实装更新的版本 | `OFM 2.7.3 · 官方已有 2.8.0，在 OFM 自己的面板里更新即可（它自升级，不走 npm）` |
| 副本与实装一致 | `OFM 2.7.3 · 官方最新（已核对 manifest） · vendor 副本已同步，重装不会退版` |
| vendor 副本落后实装 | `⚠ OFM vendor 副本 2.7.2 / 实装 2.7.3：装或卸任何插件都会退回 2.7.2` |
| 声明指向 registry | `⚠ …那是另一个包（npm 最新只有 2.1.0）…` |

「vendor 副本」是 `profiles\desktop\vendor\dsh-our-free-model-X.tgz`，pnpm 离线装用的副本。
**它才是真正的风险点**：OFM 热更只改 `node_modules`，副本不会跟着动，于是下一次任何一次
`pnpm install`（装/卸任意插件都触发）都会把实装退回副本那个版本。

官方最新版是**去仓库 manifest 问**的（四条镜像取最大版本号，30 分钟缓存）。
不查 npm —— 同名包是别人的，查了只会误导。

**OFM 升级后要做的**（实现方的活，不是维护方的）：拿官方 manifest 逐文件 SHA256 核对实装 →
把实装重新打成 `vendor/dsh-our-free-model-<新版本>.tgz` → 改 `package.json` 声明 →
`pnpm install --lockfile-only` 刷 lock。核对**源**和**打出来的产物**两头都要做。

### OpenCode 免费车道需要本机 Bun（2.7.3 起）

2.7.3 公告那句「使用前提：默认 OpenCode 免费推理需要用户自行安装原生 Bun」的意思是：
**`opencode.ai/inference/` 这条官方车道的传输改由一个本机 `bun.exe` 子进程代发**，
找不到 Bun 就直接抛 `Bun executable not found`，请求根本发不出去。

只影响这一条车道。代码里明写 "Only the official OC inference lane uses Bun"，
Kilo / EAC / 账号渠道 / 目录查询全走普通 fetch。

**安装**（winget，官方包，别用 `irm bun.sh/install.ps1 | iex`）：

```powershell
winget install --id Oven-sh.Bun --exact --source winget
```

装完还要让 OFM 找得到它 —— OFM 的查找顺序是
`OUR_FREE_MODEL_BUN` → `$BUN_INSTALL/bin` → `~/.bun/bin` → PATH → `%APPDATA%\npm\node_modules\bun\bin`。
winget 装到的是 `WinGet\Packages\...\bun-windows-x64\`，**不在这个列表里**，
而当前 DSH 进程的 PATH 也还是旧的（winget 说"重启 shell 以使用新值"）。
想**不用重启**就生效，把 `bun.exe` 复制到第一顺位：

```powershell
New-Item -ItemType Directory "$env:USERPROFILE\.bun\bin" -Force
Copy-Item "$env:LOCALAPPDATA\Microsoft\WinGet\Packages\Oven-sh.Bun_*\bun-windows-x64\bun.exe" "$env:USERPROFILE\.bun\bin\"
```

**安全性**：Bun 是 Oven 出的 MIT 运行时，和 Node 同级；OFM 用它的方式很克制 ——
子进程执行的是**内联固定源码**（不是下载来的），落系统临时目录、权限 `0o600`，
源码里没有 eval / 动态 import / child_process，只做 `fetch` 并回传字节流，
stderr 直接丢弃（不吐 URL/凭据/正文）。**风险不在 Bun，在装法。**

**兜底**：`OUR_FREE_MODEL_FREE_TRANSPORT=node` 退回旧传输。但 2.7.3 上 Bun 就是为了修
免费车道兼容，退回去大概率等于退回旧故障 —— 只当应急用。

**缺 Bun 的错误已经被认得**：内置规则 `b10`（`缺Bun-装Bun即好`，`fix: "dead"`）。
它对这条路由判死、不再派，而不是归成「未知」去烧队长一次待判。装上 Bun 即可恢复。

### 「队长」标签的判据：只看清单+归档，不看 agent 热度（2026-10-30 修）

以前有两道存活剪枝，**都是错的**，一起造成「开着的队长在台账里没标签→隔壁直接派了它的模型」：

| 旧判据 | 为什么错 |
|---|---|
| `s.agent !== true` 就踢 | agent 是 cold 的**不等于**会话没了。维护方开着对话但一阵没说话，agent 自然冷下来 —— 一冷就被踢出队长名单，它那条路由掉回可派池 |
| 最近 30 分钟没活动就踢 | 维护方可能开着对话几小时不动，那照样是他的队长 |

**现在的判据只有三条**：在这个工作区的会话清单里 + 未归档 + 非子会话 + 非空白。
不看 agent 热不热、不看多久没动。真 ghost（删掉或归档的对话）由**归档名单**和**清单本身**负责。

还有一处反向的错一起修了：清单过滤后一条不剩时，旧代码**保留旧值** —— 那会让已经删掉的
对话继续顶着「队长」永久占路由。现在空集也照写（空集 = 此刻没有队长）。

### 成员撞上「长墙」要自动换路由（2026-10-30 修）

原规矩是「限流只退避、不换模型」—— 对**队长**成立（队长换不换由维护方决定），对**成员不成立**。

实录：隔壁 auto1 撞上 cline 账号池墙 `当日免费额度已用尽（HTTP 429），预计 14 小时后重置
（2026/10/31 13:41:17）`，规则 `模型账号池限流-有解禁时间` 的处置是 `backoff`，
于是它被钉在一条**到点前绝不会被派出**的路由上，整队从 23:44 空转到次日 13:43。

现在分两类：

| 墙的剩余时间 | 处置 |
|---|---|
| < 15 分钟（抖动、临时限流） | 只退避，不换路由 —— 换了也一样撞，白烧一次选路 |
| ≥ 15 分钟（长墙，且上游给了明确解禁时刻） | **换一条现在就能跑的路由**，换完发通知给队长 |

「上游给了明确时刻」的解析以前只认「将于 <时间> 解禁」一种写法，cline 那条
`重置（2026/10/31 13:41:17）` 一个字都匹配不到，14 小时的墙被当成 2 分钟退避，到点再撞一次。
现在 `将于/重置/解禁/恢复/可用` 都认，时间戳带不带括号都行。

换路由有两条入口，一条管「下次」，一条管「已经卡住的」：

| 入口 | 什么时候跑 | 管什么 |
|---|---|---|
| `recordFailure`（agent/error） | 成员这次报错时 | 新错误：判完规则顺手看看墙还剩多久，够长就换 |
| `sweepBoards`（10 秒 tick） | 一直在跑 | 存量成员：已经钉在长墙上的，不用等到点，当场换 |

自愈有三道闸，缺一条都会帮倒忙：

- **只动闲置成员**：正跑着（`running`）的不打断 —— 它可能马上就结束，中途换路由会让它下次请求突变；
- **5 分钟节流**：按 `session|route` 记，池子里真没有能跑的路由时不至于每 10 秒往队长那里推一条「换路由失败」；
- **换完立刻派活**：`dispatchSafely` 直接叫它去领 open 单，不等下一次人肉 `team` 调用。

### 退避中的路由必须出现在台账里，并带实时倒计时（2026-10-30 修）

维护方报的原话：「报错的模型也没有被插件添加倒计时关闭」。

根因不是没记 —— 台账里 `backoff` 字段是有的，`errClass` 也在。是**前端把它整行丢了**：
列表只渲染 `status === "ok" && whitelist === "allow" && groupHalt == null && backoff == null` 的行，
退避中的路由全被过滤掉，于是那段「限流至 …」的 chip 成了**永远跑不到的死代码**。
后果正是最糟的一种：成员正撞着 14 小时的墙、面板一条都不显示，看的人只会觉得「插件没反应」。

现在台账分三段渲染：

```
队长（金标）
  └ 可用（成员在用 → 空闲）
  └ 退避中（蓝 chip「限流 3小时12分」/ 橙 chip「退避 2分08秒」，按到点先后，最急的在前）
```

- 倒计时**逐秒走**（`useTick` 每秒把 `now` 传给每一行），不是到点才刷新；
- 到 0 的那一刻该行自己变回可用绿点，不必等下一次快照；
- 退避行**不进「可派」计数**（stat 卡片的「可派 N」照旧只数真正能派的），
  Section 标题尾巴单独标一个「· 退避 N」；stat 卡片上那个「失效 · N 退避」的 N 也改用同一组数，
  不许两套口径；
- 组熔断的行仍旧一条不列（整池没额度是另一件事，走标题尾巴的「· 组停 N」）。

## 推理强度：任务说需求，插件换算档位（#11）

Lead 只标**任务要多深**，不必去猜某个模型叫什么档：

| 任务 `demand` | 含义 | 换算规则（按该路由自己的档位表） |
|---|---|---|
| `1` | 机械、不用想 | ≤ low 里最高（没有 low 才退 none） |
| `2` | 常规（缺省） | ≤ medium 里最高（没有就 low） |
| `3` | 高推理 | ≤ high 里最高（没有就 medium）— **默认天花板** |
| `max` | 顶格，慎用 | 该路由**自己的最高档**（xhigh/max）；不是全局 rank 5 |

- 各路由档位串有 7 种写法（`low/high/max`、`none/low/medium/xhigh`、甚至倒序 `high/none`），所以按**规范 rank**（none/disabled 0 < low 1 < medium 2 < high 3 < xhigh 4 < max 5）取，绝不按字符串位置取。
- **切档发生在派单那一刻**（`maybeDispatch`/`claim`/`spawn` 首任务/`msg` 带 demand），不是建成员那一刻；成员档位走 `agent/request` 每请求覆盖，所以改完下一个请求就生效，不用重建成员、不用重派。
- **实测封顶**（`封顶:high`）：真派 ok 的档会抬高上限，`档位不支持` 的档按 TTL（默认 24h）压下一档。**单次拒绝只降一档、不判死**——降档后同任务重跑一次，低档成功才把上限坐实；一路降到最低档还被拒，才判 `invalid`。
- **欠档 vs 封顶**是两回事：`欠档` = 该路由 catalog 最高就到这儿（如 d3 派给 low/medium 路由→medium）；`封顶` = catalog 有更高档但实测吃不下。两种都会在派单时推一条 `档位不足` notice，任务照跑（软筛，不硬拒——队里没有达标成员时硬拒会把任务饿死）。
- 手动清证据：`team(scan, reset:"efforts")` 清空所有实测封顶与档位拒绝记录。

## 能力矩阵：ctx 是硬门槛，out 只决定分几批写

Lead 拆任务时**只按「要读多少东西」拆，不按「要产出多少」拆**——这是两条完全不同的约束：

| 维度 | 能不能绕 | 插件怎么处理 |
|---|---|---|
| **ctx 不够** | **绕不过**。内核会**静默压缩**历史，模型在失真上下文里继续干，交出来的东西看着完整其实是错的 | `size` 声明输入要多大（s/m/l/xl = 128K/256K/1M/2M）。`task create` 时若池子里已知最大值不够，**直接拒**；派单时目标成员 ctx 不够，推 `ctx 不足` notice |
| **out 不够** | 能绕。同一任务、同一成员，分几次写文件即可 | **不拆任务**。派单消息按该路由 out 标称值自动追加「单次输出上限标称 XK：超过就分批写文件」 |

**诚实标注是硬规则**（冷启动的 Lead 会照字面理解）：

- `ctx=1.05M(标称)` / `out=131K(标称)` —— catalog 声明，**不是实测**
- `ctx=无数据` —— 插件不知道，**不能当无限、也不当 0**；这类路由只配 `size:s` 的小活，选型理由里会写明「能力不承诺」
- `封顶:medium` —— 这才是实测（真派过）
- 「能力阶梯」把**已知 17 条**和**无数据 22 条**分开算，绝不混成一个数

实测参考（2026-10-28，40 条可派）：ctx 标称 ≥1M 6 条 / ≥512K 7 条 / ≥256K 13 条 / ≥128K 16 条 / 无数据 22 条；单次输出最大 461K（仅 1 条）、≥131K 7 条、≥33K 15 条。**ctx ≥2M 或产出 ≥461K 的任务，池子里一条都接不了。**

## 压缩提醒：只在真压缩那一刻说话

**维护方定的规矩**（2026-10-30）：**压缩发生了才提醒；全程不出现压缩，压根不要提醒。**

插件不做任何预测 —— 不读占用率、不算压缩线、不猜"快到了"。那套（`ctxWarnAt`/`ctxHurryAt` 70%/90% 双档扫描）已被删除：压缩什么时候来不可预测，猜它必然误报。

只听内核事实。内核 `@deepseek-ai/dsh-compaction-basic` 在压缩时 append 两个事件：

- `compaction/start` —— 开始
- `compaction/end` —— 收尾。**成功的 end 带 `compactionId`+`turn`；失败的 end 带 `error` 字段**

所以判断条件是 **`data.error === undefined`**：压缩失败的 end 不算压缩（上下文原样还在，去提醒就是误报）。

触发后给被压缩的会话发一条（**成员和队长都发**，队长自己的上下文一样会被压）：

> 【上下文已被压缩】… 摘要之外的内容你**已经不再拥有**。
> ① **最终产出不可仅凭记忆**：已有结论/数据/路径立刻落盘；干完就 finish，别拖。
> ② 要细节按粒度往下查：上下文里的 archive 索引只是**大概**；再具体 `ctx_search` 查 CTX 库（原文片段）；要一字不差就拆 ZSTD 会话底档（**原文全在，一条没删**）。
> ③ 最容易犯的错不是忘，而是**忘了却以为没忘**：要用的文件重新 read 一遍；发现可能在重复劳动，立刻上报队长。

同时给队长一条 `成员被压缩` 通知（队长看不见成员被压，但能决定收单重派）。

- 防刷屏：同一成员 10 分钟内连压两次只说一次（`compactNoticeMinGapMs`，默认 600000）；不同成员各自记账。
- 状态落 `.state/compact-notice.json`，重启后仍生效。
- 自测 `verify-compact-notice.mjs` 12/12。

**三层粒度（查东西时按这个顺序想）**：

| 层 | 粒度 | 回答什么 |
|---|---|---|
| 压缩后的上下文 | 知道个大概 | 这段大概发生了什么、结论在哪 |
| CTX 库 | 大概上知道点细节 | 具体哪一条、哪句原话、哪个数值 |
| ZSTD 会话底档 | 原文 | 完整逐事件，一字不差、一条不删 |

## 派活分工：goal 写一次，task 只写边界

- `goal` = 整队目标 + 验收标准 + 背景，**只写一次**
- `task.body` = **只写本片边界**（产出路径、验收命令、不要碰什么），一两句
- **派单消息会自动把 `goal` 前 300 字带给成员**，所以 body 不必再抄一遍背景——抄了就是每个任务各付一次 token

## 自动领单的闸门（防 429 风暴）

- 全队同时 running ≤ `maxConcurrent`（默认 8）；
- 同一 `provider/model` 同时只跑 1 个成员（**同 provider 的不同 model 可并行**）；
- 近期失败/限流的 provider 自动退避（60s 起、30min 封顶）；**上游报错里写明恢复时刻的**（如 Qoder「最近一个将于 2026-10-31 00:00:00 解禁」）直接退到那个点 +2min，优先于周限/日限/指数退避；退避中的路由不算「可派」，面板绿点降黄、chip 显示「退避至 MM-DD HH:mm」。
- 任务带 `caps` 标签时按成员 `caps` 匹配领单。

不想让插件自己派单：`config: { autoClaim: false }`，全部改手动 `claim`/`msg`。

### 补员判据：可领单数 > **能干活的人数**才补（2026-10-30 修两轮）

**第一轮**修的是「有人闲着就不补」→ 改成「按并发算」。**第二轮**（维护方原话
「跟队长说有什么用？是插件派人」）修掉了遗留的坑：人数算的是**名册人数**，
不是**能干活的人数**。

真身：隔壁 auto1 撞 cline 14 小时墙后，`ready=1`（只剩 t9 能领）、`team.length=1`（auto1），
`1 ≤ 1` 判定"人够了"—— 可 auto1 那条路由一分钟都干不了，有效兵力明明是 0。
结果那 14 小时插件一次都没补人，队长干等 23 分钟后自己把 t9/t10 干了。

| 情况 | 动作 |
|---|---|
| 可领单数 ≤ **能干活的人数** | 不补（人够吃了，别浪费名额） |
| 可领单数 > 能干活的人数 | 补一个（这才有并行） |
| 全队 running ≥ `maxConcurrent` | 不补（并发满了） |
| 在册人数到 `maxMembers` **且没人撞墙** | 不补 |

「能干活」= 不在退避墙里、不在组熔断里（`isDeadWeight`）。撞墙的成员**不占名额**，
否则「名额已满」会挡住补人，又变回等着一条解禁 14 小时的路由。

一般成员撞墙时插件**不吭声、自己补人接上**；唯一会开口的是这单**预指派**在它身上
（只有它能领，别的成员抢不走），这时提示改派 —— 否则那单会默默卡到解禁。

「可领」= `status:open` + `owner` 为空 + `blockedBy` 全部已结（failed 也算解除）。
预指派单（`owner` 有值）不算可领 —— 它只属于那一个人。

### 拆单当场算并行度：纯串行会当场提醒（2026-10-30 加）

拆单的价值**只在并行**。建单那一刻插件就把整板算一遍「同一时刻最多能开几个工」，
纯串行会当场说出来，不用等跑完才发现「我拆了四单却只有一个人」。

判据是**最大层宽**（按 `blocked_by` 拓扑分层后的最宽一层），**不是"有没有依赖"**：

| 形状 | max | 判定 |
|---|---|---|
| `A→B→C→D` 一直串到底 | 1 | ❌ 报警「这批全是串行，拆了等于没拆」 |
| `A→(B‖C)→D` 菱形（中间并一段） | 2 | ✅ 允许，正常流水线 |
| `A→(B‖C‖D)→E` 扇出再收拢 | 3 | ✅ 允许 |
| `A→B→(C‖D)→E` 两头串中间并 | 2 | ✅ 允许 |

**骨架串行、中间能并行是允许的**（维护方 2026-10-30 明确）。插件只在"每一层都恰好 1 张单"
时才说话 —— 那才是真正的一个人从头干到尾。

依赖若成环（`blocked_by` 事后被 `set` 改成 `a→b→a`），分层和链条都会断环处理，不会挂死 tick。

### 预指派只认本队成员名（2026-10-30 修）

`task(action2:"create", owner:"…")` 的 `owner` **必须是本队名册里真实存在的成员名**。

隔壁踩过一次：`owner:"c290ae2e"` 填的是**队长自己的会话短号**，插件沿用参考实现收下，于是这单
「预指派给一个不存在的人」—— 成员按规矩不能抢（预指派只许 owner 领），自动补员也不补
（它能领但 owner 不是它），单子永久卡死。

现在建单当场校验：认出会话短号 / 会话 id、或者名字不在名册，**直接拒**，
并把本队成员名清单回给你。想让插件自动派人，就别填 `owner`。

## 静默卡死（调了模型、不思考、不回复、不报错）

内核不是没有防线，分两层（都已核对源码）：

- **流空闲看门狗**：`llm-deepseek` 和 `llm-pi-ai` 都包了 `idleWatchdog(streamIdleTimeoutMs)`，默认 `300000ms`。只有"一次读挂着"才计时，串流每来一块就重置；超时抛 `LLM_STREAM_IDLE_TIMEOUT` → `LlmError(..., "TIMEOUT")`。
- **自动重试**：`dsh-llm` 的默认 retry 策略 `maxRetries: 5`、可重试码含 `TIMEOUT`/`EMPTY_RESPONSE`/`TRANSPORT`/`SERVER`/`RATE_LIMIT`。所以卡死会**换同一路由静默重发**，最坏约 25 分钟里成员一直是 `running`、零输出、零报错——这才是真正看不见的坑。
- **空回复**：pi-ai 收到 `stop` 但 content 为空 → `EMPTY_RESPONSE`（可重试）。

插件层补的是"看得见"：每 10s 扫一遍 running 成员，若既无流帧也无会话事件

- ≥ `stallNoticeSec`（默认 360s，压过一次内核超时）→ 推一条 `成员静默` notice（成员/路由@effort/tid/静默分钟数/怎么停）+ 归档 `kind:"stall"`；
- ≥ `stallEscalateSec`（默认 900s）→ 再推一条，建议 `team(kill)` 换路由重派；
- 一旦有流帧或任何会话事件立刻清零，不重复吵；**永不自动 kill**（慢路由停不停是 Lead 的决定）。
- `team(status)` 的 stuck 列会显示 `静默 720s`，和 `loop×N`、`卡住 Ns` 并列。

## 已知边界

- 白名单 `allowedModels` **只读不写**：同步时发现"catalog 免费但白名单未开"会在 status/models 里点名，改配置要维护方拍板（且需重启+新会话生效）。
- 插件重启后成员路由靠 roster 恢复；`actual` 列来自成员会话的 durable request header，是"真跑过"的证据，不是猜测。
- 成员之间不互发（Lead↔成员够用）；需要成员对话请继续用 `send_message`。
- **写根 = 沙盒边界**：DSH 的 `workspace-write` 边界是会话 cwd（sandbox-policy: `workspaceRoot = session.header.cwd`），所以插件给每个成员单独 cwd 并钉 `workspace-write`。成员之间天然不越界；**读不受限**，只限写。要给成员两个互不相关目录，只能拆任务或把它们的父级给它。
- **写根出 `workspaceRoot` 要先问维护方**：插件不拦（只记 `(外)` + 留痕），靠 Lead 自觉；一次授权只对一个目录有效，不缓存。
  （`workspaceRoot` 默认按插件安装位置推导，不是写死的盘符；装了之后要写进自己工程目录就在 profile 里改这一项。）
- **冷启动可见性**：别的会话第一次用 `team` 时，能读到的**只有工具自带的 612 token 说明**（没有 README、没有本文件）。所以「何时用它、provider/model 从哪来、create/finish 契约、status 列怎么读」必须全在那段说明里；改说明就是改冷启动体验，改完仍需 remove→install 才生效。
- 跨队：`status(scope:"all")` 能看见**别的会话挂着的队**（成员行带 `本队`/队尾6位标签，另附每队 `成员数|open/claimed/done|活冷`）；`teams` 除 `Teamstate\` 存档外也给 `live` 列表。但**任务板只读不跨写**——不能替别队建任务/发消息，也没有发言历史与成员最终输出。
- 成员产出读回：`history(to)` 直接读该成员会话的文本事件（源是 DSH 自家服务 `sessionQuery.observeSession`，**不依赖任何第三方插件**——dsh-context 那个「通讯记录」面板读的是同一个服务，卸掉它本插件照常工作）。`filter` 传子串可在历史里捞关键词。
